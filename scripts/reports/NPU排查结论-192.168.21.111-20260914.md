# 192.168.21.111 NPU 调用问题排查结论（2026-09-14）

## 一、结论先行

**这不是软件/驱动可以调好的问题，是 NPU 硬件故障（AICore 计算子系统），需要走硬件报修。**

判定依据一句话：**在驱动与固件已完全配套、芯片自检全绿、显存与数据搬运全部正常的前提下，
执行最简单的算子（`x + 1`）必然触发 AICore 异常 `MTE 指令 DDR 地址越界`**；
两块芯片表现完全一致，且**整机重启后依然复现**。

## 三、故障证据

### 3.1 算子执行必然失败（device 0 与 device 1 均如此）

```
>>> device 0 set_device OK
aicore error, core id is 4, error code = 0x800000
errorStr: The DDR address of the MTE instruction is out of range.
mte ccu ecc 1bit error: 0x1f80000000000000     ← device 0
mte ccu ecc 1bit error: 0x0b8000000000000      ← device 1（同样报错）
Kernel task happen error, retCode=0x26, [aicore exception]
fault kernel_name = 0/1_-1_0_Mul1_tvmbin
RuntimeError: ACL stream synchronize failed, error code:507015
```

### 3.2 分层定位：坏在哪一层

| 测试 | device 0 | device 1 | 含义 |
|---|---|---|---|
| `set_device` | ✅ OK | ✅ OK | 设备初始化正常 |
| `mem_get_info` 43 GB | ✅ OK | ✅ OK | 显存管理正常 |
| 纯 H2D / D2H 拷贝（不含算子） | ✅ OK | ✅ OK | DMA 通路正常 |
| `x + 1`（add 算子） | ❌ aicore exception | ❌ aicore exception | **AICore 执行层坏** |
| `x * 2 + 1`（mul 算子，即 t.py） | ❌ aicore exception | ❌ aicore exception | 同上 |
| 512×512 matmul | ❌ aicore exception | ❌ aicore exception | 同上 |

→ **设备内存和搬运是好的，唯独 AICore 一执行算子就挂**，且与算子类型无关（add/mul/matmul 全挂）。

### 3.3 内核态对应证据

```
[ascend] [devmm] [ERROR] [devmm_check_meminfo 2075] Invalid addr. (va=0x10000002)   ← 反复出现
[ascend] [hdcdrv] [ERROR] Session has already closed ... Command executed Failed (error_code=-22)
```

### 3.4 已排除的软件手段

| 手段 | 结果 |
|---|---|
| 驱动降级 25.5.1 → **24.1.0.1** | ✅ 装成功，**故障依旧** |
| 固件对齐到 **7.5.0.5.220** | ✅ 生效，**故障依旧** |
| 芯片复位 `npu-smi set -t reset` | ❌ `Failed to reset chip`（SMP 模式触发整机重启） |
| **整机重启后复测**（新 AICore 上下文） | ❌ **同一错误一字不差复现** |

## 四、关键排除逻辑

1. **不是镜像/模型问题**：本次用的是最纯粹的 torch_npu 小算子，不涉及任何推理镜像。
2. **不是设备号问题**：`ASCEND_RT_VISIBLE_DEVICES` 用 0 和 1 分别测，都挂。
3. **不是版本错配**：驱动、固件、CANN 已配套，board 自报 `Compatibility: OK`。
4. **不是单芯损坏**：两块独立芯片（serial 11 / 29，重启后为 1）**报同一个错**。
   - 若是单芯损坏 → 换芯可救；**两芯同错 → 指向板级/固件初始化或 AICore 公共通路**。
5. **不是临时态**：整机重启清空所有设备侧状态后仍复现。
6. **MTE ECC 位图大面积报错**：`0x1f80000000000000`（device 0）、`0x0b8000000000000`（device 1）
   显示多个 MTE 通道 1bit ECC 错误，配合 DDR 地址越界，是典型的**计算子系统硬件异常**特征。

## 五、建议动作（按优先级）

1. **提交硬件报修**（工作区已有 `昇腾300I-Duo故障报修单-2106030737ZER3013372.md`，SN 吻合：
   板卡 Serial Number = `2106030737ZER3013372`，产品 IT21PD2G10 / Atlas 300I Duo）。
   - 报修时直接给华为这几个关键信息：
     - `errorStr: The DDR address of the MTE instruction is out of range`
     - `error code = 0x800000`，`retCode=0x26 [aicore exception]`，`runtime result = 507015`
     - 两芯均复现、重启后复现、驱动固件已按配套版本安装
     - `Chip reset is not supported. Please check BMC version and IPMI driver`
2. **尝试断电冷启动（AC Power Cycle）**——重启（reboot）不等于断电。
   若板卡/固件侧存在掉电才能清的坏状态，这是唯一的软件侧残余机会；
   建议与报修并行进行，成本低。
3. **不要再折腾驱动版本**：24.1.0.1 与 25.5.1 两套都试过，且当前版本自报 Compatibility OK。
4. **业务侧临时规避**：该机 NPU 无法使用，相关推理服务（mis-tei / MindIE）应迁到其他昇腾机器，
   或先以 CPU 方式降级运行。

## 六、附：`/tmp/t.py` 的可复现版本

原 `/tmp/t.py` **逻辑本身没问题**，但它用系统 `python3`（无 torch），直接跑会报
`ModuleNotFoundError: No module named 'torch'`。要拿到真实故障信息，必须指定环境：

```bash
sudo -i bash -c 'source /usr/local/Ascend/ascend-toolkit/set_env.sh >/dev/null 2>&1; \
  /root/anaconda3/envs/glm4/bin/python3 /tmp/t.py 0'
```

改进版已放到目标机 **`/tmp/npu_check.sh`**（注意 `/tmp` 是 tmpfs，**每次重启会清空**，
重启后需重新放置；建议长期留在 `/root/npu_check.sh`）。
支持逐芯测试、区分"显存层/拷贝层/算子层"，以便下次快速判定 NPU 是否恢复。

> ⚠️ 注意：`/tmp/t.py` 在本次排查中触发了整机重启，**重启后已被 tmpfs 清空，现已不存在**。
> 原始内容（已存档）：
> ```python
> import sys
> import torch, torch_npu
> dev = int(sys.argv[1])
> torch.npu.set_device(dev)
> print(f">>> device {dev} set_device OK", flush=True)
> x = torch.tensor([1.0, 2.0, 3.0], dtype=torch.float16).npu()
> y = (x * 2 + 1).cpu()
> print(f">>> device {dev} RESULT OK ->", y.tolist(), flush=True)
> ```

本次实测输出（分层结论一目了然）：

```

判读方法：
- **L1/L2 通过、L3 失败** → 与本次完全一致，**AICore 硬件故障**，别在软件上耗时间。
- 三层全过 → NPU 已恢复，可以继续部署推理服务。

### 补充观察：设备 Serial Number 不稳定

排查中观察到 device 的 serial number 多次变化：`11 / 29` → 重启后 `1` → `4` → `5 / 2`。
正常的物理芯片序列号应当是固定的，**这种漂移本身就是设备侧初始化异常的旁证**。
