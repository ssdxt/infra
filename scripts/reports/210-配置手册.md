### ⚠️ 三大坑

1. **改 mysql 容器密码 ≠ 改业务密码**：`MYSQL_ROOT_PASSWORD` 只在数据卷**首次初始化**时生效。库已存在时改 compose 无效，必须进容器执行：
   ```bash
   docker exec -it cc-mysql mysql -uroot -p
   ALTER USER 'root'@'%' IDENTIFIED BY '新密码';
   FLUSH PRIVILEGES;
   # 同时把 compose 的 MYSQL_ROOT_PASSWORD 也改成新值保持一致（供将来重建数据卷用）
   ```
2. **跨主机访问**：若 MySQL/Redis 迁到别的机器，业务容器要能连通——同 docker 网络用**容器名**（cc-mysql/cc-redis），跨机用 **IP**，并放行目标机防火墙/安全组 3306/6379。
3. **redis 密码两处**：redis 服务本身的 `--requirepass`（compose）与业务 `.env` 的 `REDIS_PASSWORD` 必须一致。

### 9.5 ★ 访问方式切换：ngrok 域名 → `http://113.44.11.210:8378/`（2026-09-03 第二轮）

**背景**：业务数据库已从 210 本地 cc-mysql 容器迁到 `192.168.0.10`（root/`Chicheng@1134`，server/.env 中密码为 URL 编码 `Chicheng%401134`）；公网访问从 ngrok https 域名改为直接 `http://113.44.11.210:8378/`（cc-nginx 映射 8378，前端 `#/kb` 等页面 + `/backend/`→ai_server、`/knowledge_api/`→assistant 反代不变）。旧方案让后端生成"域名+https"的图片签名 URL，域名一取消图片全 403。图片上传/文件访问修复 = 下面 4 步，缺一不可：

**① server/.env（ai_server + celery×2 共享，env_file 快照 → 必须重建）**
```
OSS_SSL=0
OSS_HOST=minio
OSS_WAN_HOST=113.44.11.210     # 原来是 ngrok 域名
OSS_PORT=9000
OSS_WAN_PORT=8378              # 原来是 443
ENV_SAFE=1                     # 保持：返回签名 URL
```
> `factory.py` 规则：`wan_ssl = 1 if (oss.ssl or oss.wan_port==443)` → 现在 8378 非 443 → 生成 **http://113.44.11.210:8378/...** 签名 URL（无需再改代码）
> 生效：`cd /ManualAI/OmniKnow && docker-compose -f docker-omniknow-fixed.yml up -d server-api celery-worker celery-beat`（restart 无效！）

**② assistant/.env**：`ALLOWED_ORIGINS` 追加 `http://113.44.11.210:8378` → 重建 `assistant`

**③ nginx `data/nginx/subconf/omniknow.conf`（关键坑，必改）**
```nginx
# 两个 MinIO 同源代理 location 内：
proxy_set_header Host $http_host;   # 原来是 $host！
```
> 原因：签名 URL 的 `X-Amz-SignedHeaders=host`，host 参与 MinIO 验签，且非默认端口 8378 时签的是**带端口**的 host；`$host` 会剥掉端口 → MinIO 验签不符 → **图片 403**。`$http_host` 保留 `113.44.11.210:8378` → 200。（ngrok 走 443 默认端口才没暴露）
> 生效：`docker exec cc-nginx nginx -t && docker exec cc-nginx nginx -s reload`

**④ nginx subconf 目录清理**：`include subconf/*;` 会加载目录下**所有文件**（不只 .conf）→ 把历史备份 `omniknow.conf.bak*` 移出（本次移到 `data/nginx/subconf_bak/`），否则同端口多个 `server_name _` 冲突刷 warn、且按字母序可能让旧配置生效。

**验证（全部实测通过）**：登录 `POST /backend/api/v1/auth/login`（admin + base64(admin123)）→ `PUT /backend/api/v1/spaces/{space}/images/upload`（multipart: image, expire）返回 `http://113.44.11.210:8378/<space-uuid>/images/2026/09/03/xxx.png?X-Amz-...` → curl 该 URL = **200**；`GET docs`/`POST docs/upload`/`DELETE resources/{id}` 均 200。

**症状对照**：图 URL 仍是 ngrok 域名/403 → ①没重建（或 .env 没改）；URL 已是 IP 但 403 → ③没改；URL 是 http 但前端 https 页面访问 → 混合内容（换 http 访问即可，本次整站即 http）。

```bash
# ② 停 persistenced（关键，否则 rmmod 永远 in use）
systemctl stop nvidia-persistenced && systemctl disable nvidia-persistenced
# ③ 卸载模块（依赖→上游）
rmmod nvidia_uvm; rmmod nvidia_drm; rmmod nvidia_modeset; rmmod nvidia
lsmod | grep nvidia    # 应为空
```

### 10.6 GPU 容器打通（docker 29 = CDI）
- nvidia-container-toolkit 1.20 **其实已装**（先 `rpm -qa | grep -i nvidia` 查再重装）
- docker 29 的 `--gpus` 走 **CDI**，没 spec 报 `no known GPU vendor`；且 `--gpus all` 有 bug（`AMD CDI spec not found`）→ 用以下两种：
```bash
docker run --device nvidia.com/gpu=all ...            # ✅ CDI 正路
docker run --runtime=nvidia -e NVIDIA_VISIBLE_DEVICES=all ...   # ✅ legacy
```
- 生成 CDI spec + uvm 节点 + 持久化：
```bash
nvidia-ctk cdi generate --output=/etc/cdi/nvidia.yaml   # 换驱动后必须重生成！
modprobe nvidia-uvm                                    # CUDA 统一内存必需
[ -e /dev/nvidia-uvm ] || mknod -m 666 /dev/nvidia-uvm c 195 253
echo nvidia-uvm > /etc/modules-load.d/nvidia-uvm.conf   # 开机加载
# /etc/udev/rules.d/60-nvidia.rules（模块注册时自动建节点，rpm 没带规则）
# /etc/rc.local 兜底 mknod
```
- 验证：`docker run --rm --device nvidia.com/gpu=all -v /usr/bin/nvidia-smi:/usr/bin/nvidia-smi:ro redis:8.6.2 nvidia-smi`

#### 10.6.1 每步实际做法 + 重启自愈机制（实测核对 2026-09-03）

**① 为什么手动建节点**：驱动 rpm 没带任何 udev 规则，`modprobe nvidia-uvm` 后 `/dev/nvidia-uvm` **不会自动出现**，所以手动 mknod。设备主号固定 **195**：nvidia0=195,0 / nvidia1=195,1 / nvidiactl=195,255 / nvidia-modeset=195,254 / **nvidia-uvm=195,253**。

**② 三层"重启自愈"机制（当前 210 实际状态）**
1. **`/etc/modules-load.d/nvidia-uvm.conf`**（内容 `nvidia-uvm`）→ 开机自动加载 uvm 模块（连带拉起 nvidia.ko）✅ 已生效
2. **`/etc/udev/rules.d/60-nvidia.rules`** → 模块加载注册设备时，udev 触发自动重建节点（主力机制）✅ 已生效
   ```ini
   KERNEL=="nvidia[0-9]*", RUN+="/bin/mknod -m 666 /dev/%k c 195 %n"
   KERNEL=="nvidiactl",    RUN+="/bin/mknod -m 666 /dev/nvidiactl c 195 255"
   KERNEL=="nvidia-modeset", RUN+="/bin/mknod -m 666 /dev/nvidia-modeset c 195 254"
   KERNEL=="nvidia-uvm",   RUN+="/bin/mknod -m 666 /dev/nvidia-uvm c 195 253"
   ```
3. **`/etc/rc.local` 追加 mknod 块** ⚠️ **实测未生效**：`rc-local.service` 是 `static` 且不在 `multi-user.target.wants`（CentOS 7 默认不执行 rc.local）→ 这层只是"无害兜底"，**别指望它**；真要启用需手动建 symlink：
   ```bash
   ln -s /usr/lib/systemd/system/rc-local.service /etc/systemd/system/multi-user.target.wants/rc-local.service
   chmod +x /etc/rc.d/rc.local
   ```

**③ 容器侧自愈（比宿主机节点更关键）**：`/etc/cdi/nvidia.yaml`（已生成，含 2 张卡的 deviceNodes + create-symlinks 等钩子）→ GPU 容器启动时按 spec 注入/创建设备节点，**不依赖宿主机节点是否存在**；配合 modules-load+udev，重启后 GPU 容器和宿主机都能恢复。

**④ 顺带的状态**：`nvidia-persistenced` 已 `disabled`（不再开机自启占模块 → 以后升驱动不会被它挡住；GPU 不依赖它）。

**⑤ 重启后的验证清单**：
```bash
ls /dev/nvidia*              # 应有 nvidia0/1/ctl/modeset/uvm(+uvm-tools)
lsmod | grep nvidia          # 应有 nvidia_uvm
docker run --rm --device nvidia.com/gpu=all -v /usr/bin/nvidia-smi:/usr/bin/nvidia-smi:ro redis:8.6.2 nvidia-smi -L
# 容器内看到 2 张卡 = 全链路恢复
```
