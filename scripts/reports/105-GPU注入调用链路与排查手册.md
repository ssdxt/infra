# 105（Jetson Thor）GPU 容器注入调用链路与排查手册

> 适用机器：192.168.21.105（Jetson AGX Thor，L4T R38.4.0，Ubuntu 24.04 aarch64）
> 数据采集：2026-09-09 · 关键版本：Docker 29.3.1 / nvidia-container-toolkit 1.18.1 / driver 580.00 (openrm)
> 用途：理解"容器怎么拿到 GPU"的完整链路，遇到"容器里没 GPU / nvidia-smi 异常 / 该不该动 CDI"等问题时按此定位。

| 项 | 值 |
|---|---|
| GPU | NVIDIA Thor（片上 PCIe 0000:01:00.0，SoC 集成，统一内存 122G） |
| 驱动 | 580.00（openrm = NVIDIA Open Kernel Module），CUDA 13.0，GSP Firmware 580.00 |

## 1. 一句话链路

```
docker run --runtime=nvidia -e NVIDIA_VISIBLE_DEVICES=all
  → Docker(containerd) 查 daemon.json 的 runtimes.nvidia
  → nvidia-container-runtime(1.18.1) 读 config.toml: mode=auto
  → auto + NVML 可用 ⇒ 选 JIT-CDI(nvcdi)（不落盘 /etc/cdi、/var/run/cdi）
  → nvcdi 经 NVML 探测本机 GPU/驱动，内存里生成 CDI spec
       devices: /dev/nvidia0,nvidiactl,nvidia-uvm,… (+MIG)
       mounts : 宿主 driver 库 /usr/lib/aarch64-linux-gnu/nvidia → 容器
       hooks  : create-symlinks / update-ldcache / …
  → 注入到 OCI spec，runc 起容器
  → 容器内: /dev/nvidia* 在 + libcuda 可 ldconfig → vllm/nvidia-smi 可用
```

## 2. 链路各环节与"去哪查、看什么"

### 环节 ① 配置源（谁把 GPU 能力"登记"给 docker）

- `/etc/docker/daemon.json` → 定义 runtime 名字与二进制路径
  ```json
  "runtimes": { "nvidia": { "args": [], "path": "nvidia-container-runtime" } }
  ```
  查：`cat /etc/docker/daemon.json`
- `/etc/nvidia-container-runtime/config.toml` → **mode 就在这**（第 18-22 行）
  ```toml
  [nvidia-container-runtime]
  mode = "auto"          # ← 关键：auto / legacy / cdi
  runtimes = ["runc", "crun"]
  [nvidia-container-runtime.modes.cdi]
  annotation-prefixes = ["cdi.k8s.io/"]
  default-kind = "nvidia.com/gpu"
  spec-dirs = ["/etc/cdi", "/var/run/cdi"]
  ```
  查：`cat /etc/nvidia-container-runtime/config.toml`
  > 修改它用 `nvidia-ctk config --in-place --set ...`（例如设 mode=cdi）。

### 环节 ② mode 决定"用哪种注入引擎"

| mode | 行为 | 是否要 /etc/cdi yaml |
|---|---|---|
| `auto`（105 现状） | 1.18+：NVML 可用 → **JIT-CDI**；否则回退 legacy | 否（JIT 内存生成） |
| `legacy` | 老 hook 方式按 env 处理（不依赖 yaml） | 否 |
| `cdi` | 强制 CDI：用 `NVIDIA_VISIBLE_DEVICES` 匹配 CDI 设备 | 看实现（可 JIT 可落盘） |

证据（105 实测）：`journalctl -u nvidia-cdi-refresh.service` 出现
`Auto-detected mode as 'nvml'` → 证明 nvcdi/NVML 探测路径生效。

### 环节 ③ CDI spec 从哪来（两种并存，别混淆）

- **A. 落盘 CDI**（供"原生 CDI 引擎"：podman `--device nvidia.com/gpu=all`、containerd/k8s cdi annotation 等）
  - 文件位置：`/etc/cdi`、`/var/run/cdi`（config 里 spec-dirs）
  - 生成：toolkit≥1.18 由 **`nvidia-cdi-refresh.service/.path`** 自动生成到 `/var/run/cdi/nvidia.yaml`；也可手动 `nvidia-ctk cdi generate --output=...`
  - 查：`nvidia-ctk cdi list`、`ls /etc/cdi /var/run/cdi`
- **B. JIT-CDI**（runtime 内部，不写盘）
  - 当 mode=auto 且 NVML 可用，`NVIDIA_VISIBLE_DEVICES=all` → runtime 现场生成内存 spec
  - 因此 **/etc/cdi 空是正常的**，不代表注入失败

> 105 的 `nvidia-cdi-refresh.service` 开机时 failed（日志 "Driver Not Loaded"），是**开机竞态**：它启动太早，nvml 还没就绪。因为实际走 JIT-CDI 不依赖它，**该失败无影响**，只留开机红字。可 disable 消除噪音。

### 环节 ④ 设备选择入口（容器侧）

| 请求方式 | 例子 | 适用 |
|---|---|---|
| env（105 用法） | `-e NVIDIA_VISIBLE_DEVICES=all`（或 `0`/UUID/逗号列表）| docker compose 传统部署 |
| CDI 名 | `NVIDIA_VISIBLE_DEVICES=nvidia.com/gpu=all` 或 `--device nvidia.com/gpu=all` | 原生 CDI 引擎 |
| annotation | k8s/containerd 注入 `cdi.k8s.io/…` | 编排 |

### 环节 ⑤ 注入产物（验证 GPU 真的进来了）

- 设备节点：`docker exec <c> ls /dev/nvidia*` → 应有 nvidia0/nvidiactl/nvidia-uvm 等
- 驱动库挂载：`docker exec <c> sh -c 'grep -c nvidia /proc/1/mountinfo'` → 105 上 = **217**
- 动态库可见：`docker exec <c> sh -c 'ldconfig -p | grep -c libcuda'` → 105 上 = **7**（host 上是 9，正常）
- 功能验证：`docker exec <c> nvidia-smi`

## 3. 快速判定矩阵（"容器用没用 CDI / 走哪种方式"）

| 检查 | 命令 | 判定 |
|---|---|---|
| runtime 名 | `docker inspect <c> \| grep '"Runtime"'` | `"nvidia"` = 走 nvidia-container-runtime |
| env 入口 | `docker inspect <c> \| grep NVIDIA_VISIBLE_DEVICES` | 有 = env 驱动（legacy/JIT-CDI）|
| cdi annotation | `docker inspect <c> \| grep -i cdi` | 无 = 未走原生 CDI 注解 |
| 落盘 spec | `ls /etc/cdi /var/run/cdi`；`nvidia-ctk cdi list` | 空 + "Found 0" = 未落盘（JIT 或 legacy）|
| mode | `grep mode /etc/nvidia-container-runtime/config.toml` | auto/legacy/cdi |
| toolkit 版本 | `nvidia-container-runtime --version` | ≥1.18 才有 JIT-CDI + nvidia-cdi-refresh |
| 容器内设备 | `docker exec <c> ls /dev/nvidia*` | 在 = 注入成功 |
| 容器内驱动库 | `docker exec <c> sh -c 'grep -c nvidia /proc/1/mountinfo'` | >0 = driver 已挂载 |

## 4. 常见坑（都是本次实测踩过/见过的）

1. **`/proc/1/mountinfo` 必须在容器内查**：宿主机上 `grep -c nvidia` = 0 是正常的（宿主机 PID1 不挂 driver），别误判。
2. **grep 跨行陷阱**：`docker inspect` JSON 里 `"HostConfig": {` 与 `"Runtime": "nvidia"` 不在同一行，`grep -i hostconfig.runtime` 必然空。要分开 grep。
3. **拼写**：`libcuda`（不是 `lcudai`）。
4. **"Found 0 CDI devices" 是日志不是空**：`nvidia-ctk cdi list` 的输出有一行 `level=info msg="Found 0 CDI devices"`，代表 0 个落盘 CDI 设备（正常）。
5. **CDI 空 ≠ 注入失败**：105 走 JIT-CDI，yaml 目录空是设计使然。
6. **nvidia-cdi-refresh failed ≠ 故障**：开机竞态，与 JIT-CDI 路径无关；可 disable。
7. 判断容器内注入是否 OK 只看：`/dev/nvidia*` 在 + mountinfo 有 nvidia + libcuda 可加载，三者齐全即 OK。

## 5. 排查决策树（从症状出发）

```
容器里没有 /dev/nvidia* 或 nvidia-smi 报找不到设备？
 ├─ 检查 docker inspect <c> 的 Runtime 是否 = nvidia
 │    └─ 不是 → compose 缺 runtime: nvidia / daemon.json 缺 runtimes.nvidia
 ├─ 检查 env 是否有 NVIDIA_VISIBLE_DEVICES
 │    └─ 无 → 容器没声明要 GPU
 ├─ 检查宿主 nvidia-smi 是否正常（驱动层）
 │    └─ 宿主也异常 → 驱动/模块问题（看 Xid、NVRM、dmesg），不是容器问题
 └─ 全正常但容器内无设备 → 看 nvidia-container-runtime 日志（log-level=debug）

宿主 nvidia-smi 正常、某容器 nvidia-smi 无输出？
 ├─ /dev/nvidia* 在？ mountinfo 有 nvidia？
 │    └─ 都在 → 应用/镜像缺 driver 库，检查镜像是否带 nvidia 用户态（通常注入即可）
 
要不要生成 CDI yaml？
 ├─ 只跑 docker compose（env 方式）→ 不需要，JIT-CDI 已够
 ├─ 要 podman --device / k8s CDI → 让 nvidia-cdi-refresh 或手动 nvidia-ctk cdi generate 生成到 /var/run/cdi
```

## 7. 一句话总结

**105 的 GPU 注入 = Docker(nvidia runtime) → config.toml(mode=auto) → toolkit 1.18 JIT-CDI(nvcdi/NVML) → 把设备+driver 库注入 runc 容器。** 它不落盘 CDI yaml，所以 `/etc/cdi` 空、`nvidia-cdi-refresh` failed 都不影响运行；排查 GPU 问题先分"宿主驱动层 / runtime 注入层 / 容器内可见层"三段，逐层用上面的命令验证。
