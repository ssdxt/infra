# 192.168.21.111 频繁卡死（硬复位）问题排查报告

- 主机：`kzzk`（192.168.21.111），银河麒麟 V10 / Kylin，内核 `5.4.18-87.76-generic`，aarch64
- 主板：Quaitra ChaoXiang Series / DF40，BIOS `KL4.28.KZ.D.R28.250623.R`（2025-06-23）
- 内存：2 × 32 GB DDR5-4800（配置速率 4000 MT/s）
- 盘：SCY S3000 1TB NVMe（`nvme0n1`）
- 加速卡：Huawei Atlas 300I Duo（310P3，`19e5:d500`，`0000:0b:00.0`，SN `2106030737ZER3013372`）
- 报告时间：2026-09-14

---

## 一、结论摘要

**根因高度指向昇腾（Ascend）NPU 驱动 + 故障加速卡的组合，导致内核内存管理结构被破坏，最终整机硬锁死。**

三条独立证据链都指向同一处：

| # | 证据 | 说明 |
|---|---|---|
| 1 | 内核持续报 **坏页表 / 坏 swap 项 / RSS 计数错乱** | `BUG: Bad page map`、`bad pte`、`Bad rss-counter state`、`swap_info_get: Bad swap offset entry` |
| 2 | 内核 **tainted `G OE`**，调用栈落在 `exit_mmap` 时被污染的内存管理路径 | 栈顶模块列表里是昇腾驱动（`drv_soft_fault`、`drv_davinci_intf_host`、`dbl_*` 等一长串 `(OE)`） |
| 3 | **崩溃的进程全是昇腾相关进程** | coredump 统计：`mindie_llm_back` ×5、`pt_main_thread` ×2、`python-text-emb` ×1、`npu-smi` ×1 |

并且这台机器上的 **NPU 卡本身已确认故障**：任何最小算子都跑不了
（`retCode=0x26 [aicore exception]`、`errorStr: The DDR address of the MTE instruction is out of range`、
`mte ccu ecc 1bit error`），`dmesg` 还报该卡 **VPD 读取失败 / 厂商固件 bug**：

```
devdrv_device_driver 0000:0b:00.0: VPD access failed.
  This is likely a firmware bug on this device. Contact the card vendor for a firmware update
```

## 二、卡死现象的精确界定

`journald` 是 `Storage=volatile`（只存内存），硬复位就把现场全抹掉。幸运的是
`rsyslog` 把日志落到了 `/var/log/syslog`、`/var/log/kern.log`，才拿到跨重启的历史。

### 2.1 三次事件的真实性质（关键）

| 运行期 | 结束时间 | 性质 | 判据 |
|---|---|---|---|
| 08:02 → **08:26:20** | 日志**戛然而止** | **猝死（硬卡死）** | 关机类日志 **0 行**，最后一条是软件中心的正常重启日志 |
| 08:32 → 09:08:58 | 完整 `Stopping ...` / `Unattended Upgrades Shutdown` | 有序关机 | 关机类日志完整 |
| 09:10 → **09:26:57** | 日志**戛然而止** | **猝死（硬卡死）** | 关机类日志只有 1 行 dockerd 卸载报错，断在加载 `libwallpaper.so` 时 |

> 所以你感觉到的"只能用硬件重启"，对应的是 **08:26:20** 和 **09:26:57** 两次；中间 09:08:58 那次是正常关机。

### 2.2 猝死时的共同特征

全部排查项都是**否定**，这本身就是最重要的特征：

| 排查项 | 结果 |
|---|---|
| kernel panic / Oops | ❌ 0 条 |
| hung task / blocked for more than 120s | ❌ 0 条 |
| soft lockup / hard lockup / RCU stall | ❌ 0 条 |
| OOM-killer / Out of memory / Killed process | ❌ 0 条 |
| page allocation failure | ❌ 0 条 |
| PCIe AER 错误记录 | ❌ 0 条 |
| 日志尾部 | 断在**完全正常的操作中间**，无任何前兆 |

**结论：不是 OOM、不是换页、不是负载压死、不是内核自己报错——是"整机突然失去响应"。**

### 2.3 内存不是瓶颈（排除项）

- 卡死周期内 `free`：62 GiB 总量、仅用 2.6 GiB、**swap 用量 0**
- 有一个 62.5 GiB 的 swap 分区（`nvme0n1p6`），但从未被使用
- `swappiness=60`、`overcommit_memory=0`

## 三、为什么会"静默硬锁死"：机理推断

这台机器的内核**安全网全部是关闭的**，所以一旦设备侧出事，CPU 会直接失联，且**什么日志都留不下**：

```bash
# /proc/cmdline
... ro iommu.passthrough=on quiet splash loglevel=0 console=tty0 ...
```

| 配置 | 后果 |
|---|---|
| `iommu.passthrough=on` | IOMMU 不做地址翻译。设备发出非法 DMA 时，**没有 IOMMU 拦截**，直接打到物理内存 |
| `nmi_watchdog=0` + 无 `/dev/watchdog` | **没有任何 watchdog**，硬锁死后无法自动重启 |
| ACPI `_OSC` 不支持 AER | PCIe 错误**没有 AER 上报/恢复**，设备级异常静默 |
| `quiet splash loglevel=0` | 控制台内核日志被压到最低，现场看不到任何东西（与"鼠标键盘都没反应"一致） |

在 ARM 平台（飞腾 CPU）上，设备非法访问通常表现为 **SError（异步外部中止）**。
`iommu.passthrough=on` 让这个错误既不被拦截也不被记录，而 `loglevel=0` 让它不上屏——
**这与"毫无征兆、键盘鼠标全死、日志断在正常操作中间"完全吻合**。

而昇腾驱动确实在破坏内存管理结构（证据链 1、2），这就是 SError 的来源。

## 四、次要问题（会拖慢/干扰排查，但不是卡死主因）

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| 1 | **journald 不落盘** | `Storage=volatile`，`journalctl --list-boots` 只剩当前一次 | **每次硬复位都销毁现场**，这是排查最大的障碍 |
| 2 | **coredump 刷盘凶猛** | `/var/lib/systemd/coredump` 已 **4.3 GB**（单个 mindie core 达 240 MB / 1.7 GB）；根分区 98 G 已用 65 G | MindIE 崩溃循环时每分钟数百 MB 写盘 |
| 3 | **VS Code Server ripgrep 风暴** | 3 个 `rg` 进程占 CPU **346% + 285% + 197%**；8 核机器 load average 冲到 **120~175** | 机器极卡（但不会导致硬锁死） |
| 4 | **`kylin-software-center` 重启风暴** | `Scheduled restart job, restart counter is at 3666`（约每 5 秒一次） | 无谓消耗、日志噪声 |
| 5 | amdgpu 风扇读数为 0 | `amdgpu-pci-0c00 fan1: 0 RPM`，edge 52 °C | 独立显卡（Radeon HD 8570，亮机卡）；`pwm1_enable=0` 为自动模式，暂判非主因 |
| 6 | NVMe `Unsafe Shutdowns: 59` | SMART 其余全绿（`PASSED`、`Percentage Used 0%`、`Available Spare 100%`、**No Errors Logged**） | 59 是硬复位的**结果**而非原因；盘本身健康 |
| 7 | 开机 userspace 启动从 23.6 s 涨到 40.5 s | `dbus-daemon: Connection has not authenticated soon enough (auth_timeout=30000ms)` | dbus 认证超时 30 s 拖慢启动 |
| 8 | `getty@tty1` 启动次数超限 | `Failed with result 'start-limit-hit'` | 本地控制台（tty1）反复重启失败 |

## 五、已确认的 NPU 卡故障（与卡死同源）

- 最小算子 `x*2+1`（3 个 f16 元素）在 Chip 0 / Chip 1 **全部失败**
- `npu-smi` 自检却是全绿（`Health: OK`、`Chip Fault: 0`、DDR ECC 全 0）——**驱动上报通路失效**
- 已排除：驱动 24.1.0.1 与 25.5.1、固件 7.5.0.5.220、CANN 8.1/8.2/8.5、单芯片、宿主机直跑、容器内跑
- 当前状态：驱动 `24.1.0.1`、固件 `7.5.0.5.220`（已是交付文档要求的组合），仍失败

**该卡已在走报修流程**（见《昇腾300I-Duo故障报修单-2106030737ZER3013372.md》）。

## 六、待办与建议（按性价比排序）

### 立即做（零风险，只增不改行为）

1. **打开 journald 持久化**，让下一次猝死能留下证据
   ```bash
   sudo mkdir -p /var/log/journal
   sudo sed -i 's/^#*Storage=.*/Storage=persistent/' /etc/systemd/journald.conf
   sudo systemctl restart systemd-journald
   ```
2. **限制 coredump**，避免写盘把根分区吃满
   - `/etc/systemd/coredump.conf`：`Storage=external`、`MaxUse=2G`、`KeepFree=5G`
   - `/etc/security/limits.conf`：`* hard core 0`（如不需要 core）
3. **清理现存 4.3 GB coredump**（需确认后执行）

### 需要你决策（涉及业务）

4. **停掉会触发 NPU 的业务，观察是否还卡死**
   - `glm-4-9b-chat`（MindIE，`RestartPolicy=always`，`/deploy/models/docker_run/vllm/docker-compose.yml`）
   - 这是最关键的**单变量验证**：若停掉 NPU 负载后连续运行 24~48 小时不再卡死，
     则"NPU 驱动/硬件导致硬锁死"结论闭环
5. **加固内核启动参数**（需重启生效）
   - 去掉 `iommu.passthrough=on` 或改为 `iommu=pt`，让 IOMMU 能拦住非法 DMA
   - 去掉 `quiet splash loglevel=0`，改为 `loglevel=7`，让下次卡死时屏幕上有线索
   - 加 `pstore`/`ramoops` 或开启 `kdump`（当前 `crashkernel` 未配置、`/sys/fs/pstore` 为空）
6. **处理 ripgrep 风暴**：关闭 VS Code Remote 的 `search.followSymlinks` / 排除 `/deploy`、`/var`，
   或直接 `pkill -f 'rg --files'`
7. **修 `kylin-software-center` 重启风暴**（重启计数 3666 次）
8. **升级 BIOS**：当前 `KL4.28.KZ.D.R28.250623.R`，可向 Quaitra/科银京成 确认是否有更新

### 长期

9. 推进 **NPU 卡更换（RMA）**；换卡后再验证 `bge-m3` 服务
10. 若需长期保留现场取证能力，建议同时开启 `ramoops`（内核崩溃前的 RAM 日志转存）
