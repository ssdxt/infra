# etcd 高性能磁盘需求（给虚拟化/基础设施团队）

> 生成时间：2026-09-29
> 背景：K8s 集群控制面（etcd）因存储慢导致频繁故障，需为 3 台控制节点提供高性能磁盘

---

## 一、需要改造的 3 台 VM

| 主机名 | IP | 当前 etcd 数据目录 |
|---|---|---|
| **wxq-control-01** | **10.100.10.10** | /var/lib/etcd（在系统盘 vda 上） |
| **wxq-control-02** | **10.100.10.14** | 同上 |
| **wxq-control-03** | **10.100.10.19** | 同上 |

> 注意：只需改这 3 台。worker 节点（.33/.34/.39/.41/.44/.45/.46/.47）本次不动。

---

## 二、磁盘规格

| 项 | 要求 | 说明 |
|---|---|---|
| **容量** | **100GB / 台**（共 300GB） | etcd 数据实测仅 **19MB**，容量完全不是瓶颈，100GB 是留足余量与快照空间 |
| **性能** | **独立 SSD / NVMe，或独立高性能存储层** | ★ **最关键的一条，见下** |
| **来源** | **不能来自当前的共享慢存储池** | 见第三节实测数据 |
| **置备方式** | 厚置备 / 立即置零（不要 thin + lazy zero） | 避免首次写入时抖动 |
| **交付形式** | 作为独立虚拟磁盘挂给 VM（如 /dev/sdb），**无需格式化** | 我们会自己格式化（xfs）并挂载 |

---

## 三、为什么强调"不能来自当前存储池"

我们在**全部 11 台节点**上做过 fio 实测，结论是**慢的是共享存储后端本身，不是某台 VM**：

| 指标 | 当前实测值 | 正常 SSD 应有 | 差距 |
|---|---|---|---|
| 同步写（8k + fdatasync，etcd 模式） | **25 ~ 243 次/秒** | ≥1000 次/秒 | **差 5~40 倍** |
| fdatasync **p99** | 8 ~ 37 ms | ≤10 ms | 超标 |
| fdatasync **p99.9** | **616 ms ~ 2.1 秒** | ≤50 ms | **差 100 倍** |
| fdatasync **p99.99** | **1.8 ~ 4.9 秒** | ≤200 ms | **差 100 倍** |
| 顺序大块读写 | 147 ~ 662 MB/s | ≥300 MB/s | ✅ 正常（有缓存） |

**关键证据**：
1. 11 台机器**同时都慢**（不是个别机器的问题）
2. **并发测试比单台测试慢 2~3 倍** → 证明是**共享后端争抢**
3. 顺序大块 IO 正常、同步小 IO 极慢 → 典型的**缓存型共享阵列 + 无写缓存**特征

**因此：如果只是从当前同一个存储池再切一块盘，性能不会有任何改善。** 必须是独立的高性能介质（本地 NVMe/SSD，或与其他 VM 不争抢的独立层）。

---

## 四、验收标准（我们会在 3 台 VM 上【同时】运行验证）

磁盘挂上来后，先不迁移 etcd，直接在裸盘上跑：

```bash
# 格式化并挂载到临时目录后
fio --name=etcd-accept --ioengine=libaio --iodepth=1 --rw=write \
    --bs=8k --direct=0 --fdatasync=1 --size=1G \
    --filename=/mnt/etcd-new/fio.test \
    --runtime=60 --time_based --group_reporting
```

**达标线**：

| 指标 | 要求 |
|---|---|
| write IOPS（每秒成功落盘次数） | **≥ 1000** |
| fdatasync p99 | **≤ 10 ms** |
| fdatasync p99.9 | **≤ 50 ms** |
| fdatasync max | ≤ 500 ms |

**注意：必须 3 台同时跑**，因为要排除共享后端的相互争抢。

---

## 五、关于"是否必须迁移 VM"

| 情形 | 说明 |
|---|---|
| 能**直接给现有 VM 挂一块新盘** | ✅ 最理想：我们自己滚动迁移 etcd，**业务零停机** |
| 必须**把 VM 迁到新数据存储**才能真正提速 | ✅ 也可以：用存储 vMotion/迁移即可，**不需要重装系统** |
| ❌ 重装系统 | **解决不了存储慢**（底层介质慢，重装一样慢），且会导致整套集群重建 |

---

## 六、附：当前慢存储造成的实际故障（作为佐证）

- etcd 日志 `slow fdatasync` 累计 **1 万次**，单次 1.4~3.1 秒
- 内核报 `task etcd blocked for more than 15 seconds`
- etcd raft leader 选举 **150+ 次**
- kube-vip 因续租失败反复退出 → **VIP 间歇性消失**
- cilium-operator 崩溃重启 **155 次**
- Longhorn CSI 组件重启 **41 次**
- 控制面组件（scheduler/controller-manager）曾集体 CrashLoop

**结论**：这些故障的根因都是"etcd 写 WAL 时 fsync 卡住"，属于**基础设施层问题**，节点内已无优化空间（我们已把租约超时放宽到 60/40 级别做临时绕行）。

---

## 七、磁盘到位后我们的操作（滚动、业务不中断）

1. 在 3 台 control 上跑 fio 验收（同时）
2. 逐台迁移 etcd：停 etcd → 数据拷到新盘 → 改 `/etc/etcd.env` 的 `ETCD_DATA_DIR` → 挂载新盘到 `/var/lib/etcd` → 启 etcd → 验证健康（一次只动一台）
3. 三台迁移完成后，把之前为绕行慢盘而放宽的参数调回正常值（恢复快速故障切换）
