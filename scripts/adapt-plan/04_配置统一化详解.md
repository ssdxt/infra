## 一、设计：三层配置优先级

```
进程环境变量(systemd/容器/k8s 注入)  >  /deploy/deploy.env  >  代码内默认值
        最高优先，编排层覆盖              统一事实源，人改这里        兜底，保证无 env 也能跑
```

- **代码内默认值 = 老形态行为**（如 `127.0.0.1:2881`）：不部署 env 文件时系统照旧能跑，改造零破坏。
- **deploy.env = 换环境的唯一改动点**：换 IP、容器化改服务名、增删可选模型，都只改这一个文件。
- **编排层（后续容器/k8s）**：compose 用 `env_file:` 引同一个文件；k8s 用它生成 ConfigMap——三种形态共用一份配置语义。

## 二、目录关系：配置和脚本不在一个目录，怎么统一？

改造前的痛点：配置散在 `code/chat_doc_0918/configs/*.py`（Python 常量）、`code/web_0918/index.html`（JS 变量）、`cc/bash/*.sh`（脚本硬编码）、`cc/bash/*.py`（运维脚本硬编码）四处，互相不知道对方的存在。

统一后的结构（`/deploy` 是 code 和 cc 的公共父目录，env 放这里谁都够得着）：

```
/deploy/
├── deploy.env                  ← ★ 新增：统一配置（从 deploy.env.example 复制）
├── deploy.env.example          ← ★ 新增：模板（含全部变量说明+形态示例，随代码走）
├── code/
│   ├── chat_doc_0918/configs/  ← 改为 os.getenv("XXX", 默认值)，不再写死地址
│   └── web_0918/index.html     ← 改为同源相对路径（统一入口形态免改）
└── cc/
    ├── bash/api_start.sh       ← 开头统一 source /deploy/deploy.env
    ├── bash/web_start.sh       ← 同上
    ├── bash/speech_service_start.sh ← 同上
    └── bash/fix_doc_id.py / regen_qa.py ← DB 配置改为解析 DB_URI 环境变量
```

**关键机制（启动脚本开头三行）**：

```bash
ENV_FILE="${ENV_FILE:-/deploy/deploy.env}"     # 路径本身也可被环境变量覆盖（测试/多环境用）
[ -f "$ENV_FILE" ] && { set -a; source "$ENV_FILE"; set +a; }
```

- `source` 把文件里的变量读进**当前 shell**；
- `set -a` 让读进来的变量**自动 export**——这是脚本目录和代码目录解耦的核心：python 子进程通过 `os.getenv()` 就能拿到，无需 python 自己去找配置文件路径；
- `[ -f ... ]` 容错：文件不存在就跳过，全部走代码默认值（兼容还没部署 env 文件的老机器）。

于是"配置在哪、代码在哪、脚本在哪"三者彻底解耦：**脚本只负责 source + 启动；代码只管 getenv；人只改 deploy.env**。

## 三、启动方式调整说明（before → after）

以 `api_start.sh` 为例（web/speech 同理）：

```bash
# ===== after =====
ENV_FILE="${ENV_FILE:-/deploy/deploy.env}"
[ -f "$ENV_FILE" ] && { set -a; source "$ENV_FILE"; set +a; }   # ← 新增：统一配置注入
source /root/anaconda3/bin/activate recovery
cd /deploy/code/chat_doc_0918
export ASCEND_RT_VISIBLE_DEVICES="${ASCEND_RT_VISIBLE_DEVICES_API:-0}"  # ← 设备号也可由 env 控制
python startup_obd.py --all-api > /deploy/cc/logs/api_log.txt 2>&1      # ← 顺手补了 stderr 合并（排障用）
```

systemd 单元（`cc/service/*.service`）**不需要改**——它们只调脚本，配置注入发生在脚本内。
临时覆盖单个变量（不落盘）：`ENV_FILE=/tmp/test.env systemctl restart chat_doc_api` 或
`DB_URI=mysql+pymysql://... bash cc/bash/regen_qa.sh`（进程环境变量优先级最高，天然支持）。

## 四、新增服务/新增配置怎么接入（五步模板）

以后任何新服务（比如再加大模型、加图像描述服务）：

1. **定变量名**：`XXX_URL` / `XXX_KEY` 命名，登记进 `deploy.env.example`（带注释和形态示例）；
2. **代码读 env**：Python 侧 `os.getenv("XXX_URL", "")`，空值=功能禁用并返回明确提示（参考 tools_api.py 的写法），**绝不写死 IP**；
3. **启动脚本零改动**：所有 `*_start.sh` 已统一 source deploy.env，新变量自动生效；
4. **前端类配置**（如 index.html 的 base_api）：优先同源相对路径设计，避免新增可变项；
5. **容器/k8s 形态**：compose 在服务上加 `env_file: [/deploy/deploy.env]`；k8s 用 `kubectl create configmap omniknow-env --from-env-file=deploy.env`，Pod 里 `envFrom` 引用。

**判断一个配置该不该进 deploy.env**：换个环境它会变吗？会（地址/密钥/开关/设备号）→ 进；不会（分块参数、prompt 模板路径等业务常量）→ 留在代码。
