## 7.2 踩坑记录：NNAL 安装失败

**症状**
```
[NNAL] Ascend-cann-atb_8.1.RC1_linux-aarch64.run install failed
[cann-atb] [ERROR] Check owner failed, please check env ASCEND_TOOLKIT_HOME or ASCEND_NNAE_HOME is set.
[cann-atb] [ERROR] Command execution failed, [ERROR] ret code:1
```

**根因**（证据来自 `/var/log/cann_atb_log/cann_atb_install.log`）
ATB 安装器**第一件事就是自检 `ASCEND_TOOLKIT_HOME`**，当时该变量为空 → 立即退出，
日志里除这一条外没有任何其他错误。即：**NNAL 必须在 toolkit 装好之后、且先把 toolkit 的
`set_env.sh` source 进当前环境，再安装。**

> 对照成功后的日志：`Check owner success!` → `Ascend-cann-atb install success!`

**解法**——在同一个 root shell 里先 source 再装（注意 `sudo bash -c` 而不是 `sudo ./xxx.run`，
否则环境变量会在提权时丢失）：
```bash
sudo bash -c 'source /usr/local/Ascend/ascend-toolkit/set_env.sh; \
  cd /data/driver/Ascend; \
  ./Ascend-cann-nnal_8.1.RC1_linux-aarch64.run --install \
     --install-path=/usr/local/Ascend --install-for-all --quiet --nox11'
```

**第二个坑：安装路径会自动追加 `/nnal`**
NNAL 主安装包会把 `--install-path` 的值再拼一层 `/nnal`：

| 传入 `--install-path` | 实际落地 | 是否符合文档 |
|---|---|---|
| `/usr/local/Ascend` | `/usr/local/Ascend/nnal/atb` | ✅ 正确 |
| `/usr/local/Ascend/nnal` | `/usr/local/Ascend/nnal/nnal/atb` | ❌ 多一层 |

文档与服务文件（`Environment="PATH=...:/usr/local/Ascend/nnal/atb/bin:..."`）要的都是
**前者**，所以必须传 `/usr/local/Ascend`。若已装错，`rm -rf /usr/local/Ascend/nnal` 后按上表重装即可。

**第三个坑：atb 与 asdsip 不能同时 source**
安装器明确警告：*"If the environment variables of atb and asdsip are set at the same time,
unexpected consequences will occur."* 大模型场景用 **atb**，嵌入式场景用 **asdsip**。
→ 文档 doc2 §3 里那行 `source /usr/local/Ascend/nnal/asdsip/set_env.sh` **不应出现在本部署中**
（本机未安装 asdsip，且与本项目使用 atb 的定位冲突），应从手册中删除或明确标注二选一。

# 八、Docker 容器无法启动：根因与解法（2026-09-11 实测）

## 8.1 两个互相独立的原因

### 原因一：麒麟内核拒绝 tmpfs 的 `nr_inodes=1`（影响 runc 及所有普通容器）

**症状**
```
runc create failed: error during container init:
can't mask dir "/proc/acpi": mount src=tmpfs, dst=/proc/acpi,
flags=MS_RDONLY, data=nr_blocks=1,nr_inodes=1: invalid argument
```

**定位过程与证据**
- 宿主 `/proc/acpi` 存在且是空目录，`mount -t tmpfs tmpfs /proc/acpi`（不带参数）**成功**；
- 但带 `-o` 就失败，逐项测试：
  | 参数 | 结果 |
  |---|---|
  | `-o ro` | OK |
  | `-o nr_blocks=1` | OK |
  | `-o size=4k` | OK |
  | **`-o nr_inodes=1`** | **FAIL(32)** |
  | `-o nr_inodes=2 / 64 / 1024 / 65536` | OK |
- `dmesg` 给出决定性证据：
  ```
  [17415.987713] tmpfs: Bad value for 'nr_inodes'
  ```
  **这个 5.4.18-87.76-generic 内核只拒绝 `nr_inodes=1` 这一个值。**
- runc 屏蔽 `/proc/acpi` 等路径时固定传 `nr_blocks=1,nr_inodes=1` → 必然失败。

**绕过办法（已验证有效）**
Docker 对**特权容器**会清空 `maskedPaths`/`readonlyPaths`，从而完全跳过这次 tmpfs 挂载：
```bash
docker run --privileged --runtime runc ...      # ✅ 实测成功（PRIV_RUNC_OK）
docker run ...                                   # ❌ 失败
```
**而文档里的 compose 本来就写了 `privileged: true`**，所以这条路径天然可用。

> 备选方案：麒麟源内有 `crun 0.12.1+dfsg-1` 可装，可作为不走 privileged 时的替代运行时（未实测）。

### 原因二：dockerd 的 umask 是 0000，导致 Ascend Docker Runtime 自检拒绝

**症状**
```
/usr/local/Ascend/Ascend-Docker-Runtime/ascend-docker-runtime did not terminate successfully: exit status 1
```

**根因**（证据在 `/var/log/ascend-docker-runtime/runtime-run.log`）
```
[ERROR] failed to check files, error: write permission not right
   .../moby/<id>/config.json -rw-rw-rw-
[ERROR] failed to modify spec file ...: write permission not right
```
- Ascend Docker Runtime 本质是 runc 的包装器（`--version` 输出的就是 runc 信息），它有个安全检查：**OCI spec 文件不允许对 others 可写**；
- 而 `ps` 显示 `dockerd` 的 **`Umask: 0000`**，它生成的 `config.json` 权限是 `0666` → 被拒；
- `/etc/systemd/system/docker.service` 里**没有 `UMask=` 行**，也没有任何 drop-in 设置它。

**修复方案**
```ini
# /etc/systemd/system/docker.service
[Service]
UMask=0022          # ← 新增这一行
ExecStart=/usr/bin/dockerd
```
```bash
sudo systemctl daemon-reload && sudo systemctl restart docker
```

# 十五、驱动降级失败根因与修复（2026-09-11 09:52 已成功）⭐

## 15.1 真正的失败原因：GCC 警告被当成错误

`./Ascend-hdk-310p-npu-driver_24.1.0.1_linux-aarch64.run --full` 走到 40% 后报：

```
Dkms install failed
Driver_ko_install failed
Failed to install driver package, please retry after uninstall and reboot!
```

详细日志 `/var/lib/dkms/davinci_ascend/1.0/build/make.log` 里给出了根因：

```
/var/lib/dkms/davinci_ascend/1.0/build/svmdrv/pmaster/devmm_proc_mem_copy.c:2308:23:
  错误： '*((void *)&res+104)' may be used uninitialized in this function
         [-Werror=maybe-uninitialized]
cc1：所有的警告都被当作是错误
make[3]: *** [devmm_proc_mem_copy.o] 错误 1
```

**GCC 9.3.1 报了一个 `maybe-uninitialized` 警告，而内核构建开了 `-Werror`，
于是一个警告直接导致整个 davinci_ascend 内核模块编译失败。**

> 这是"老驱动 + 新 GCC"的典型坑，与硬件、与 CANN 都无关。

## 15.2 修复方法（已实测有效）✅

**用 `KCFLAGS` 关掉该警告后再编译**：

```bash
sudo bash -c 'export KCFLAGS="-Wno-error=maybe-uninitialized -Wno-maybe-uninitialized"; \
  cd /deploy/driver/Ascend; \
  ./Ascend-hdk-310p-npu-driver_24.1.0.1_linux-aarch64.run --full'
```

验证（先单独试 `dkms build`）：
```
Building module:
cleaning build area...
'make' all KERNEL_UNAME=5.4.18-87.76-generic DAVINCI_HIAI_DKMS=y TARGET_PRODUCT=mini ...
DKMS: build completed.
davinci_ascend, 1.0, 5.4.18-87.76-generic, aarch64: built
```

完整安装也通过了：
```
Driver package installed successfully! Reboot needed for installation/upgrade to take effect!
Version=24.1.0.1
Innerversion=V100R001C19SPC005B220
```

## 15.3 关键教训

1. **`.run` 后面必须带 `--full`**，否则报 `ERR_NO:0x0004 Unrecognized parameters`。
2. **同一时刻只能跑一个昇腾安装器**，否则报
   `ERR_NO:0x0094 There is already a process being executed`（本次踩过，详见第八节）。
3. 安装失败时**旧驱动已被卸载**，机器会处于"驱动卸了没装上"的状态
   （`npu-smi` 报 `libc_sec.so: cannot open shared object file`）。
   此时应尽快用上面的 `KCFLAGS` 方式重装。
4. **装完必须 `reboot`**，否则旧内核模块仍驻留内存，`npu-smi` 仍报 `dcmi -8005`。
