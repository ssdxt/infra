## 【原有功能】

KEDA（Kubernetes Event-driven Autoscaling）是 CNCF 毕业项目：为任意工作负载提供
**事件/指标驱动**的伸缩。核心组件三个（本集群 2.21.0 全部运行于 `keda` 命名空间）：

| 组件 | 作用 |
|---|---|
| keda-operator | 监听 ScaledObject/ScaledJob，代用户创建并管理 HPA，轮询触发器 |
| keda-operator-metrics-apiserver | 实现 `external.metrics.k8s.io` APIService，给 HPA 提供外部指标值 |
| keda-admission-webhooks | 校验 ScaledObject 等 CR 的合法性 |

工作方式：用户只写 `ScaledObject`（声明 scaleTargetRef + 触发器），KEDA 自动生成
名为 `keda-hpa-<scaledobject名>` 的 HPA（external metric 类型），指标名固定为
`s<触发器序号>-<触发器类型>`（如 `s0-prometheus`），并用 label
`scaledobject.keda.sh/name=<so名>` 区分。**用户不需要也不应该手写 HPA。**

> 2.21.0 命名注意：metrics-apiserver 的 Deployment 名是
> `keda-operator-metrics-apiserver`（旧文档/旧版本的 `keda-metrics-apiserver` 已不存在）。

### KEDA(prometheus 触发) vs prometheus-adapter 架构对比

| | prometheus-adapter（现状，保留） | KEDA prometheus 触发（本篇） |
|---|---|---|
| APIService | `custom.metrics.k8s.io`（+external） | `external.metrics.k8s.io` |
| 指标配置方式 | adapter 的 `rules:`（PromQL→API 资源映射，改规则要 helm upgrade） | 每个 ScaledObject 自带 query，随应用 YAML 一起交付 |
| 粒度 | 集群级全局规则 | 应用级，谁用谁声明 |
| 缩容到 0 | 不支持 | 支持（ScaledJob 或 minReplicaCount=0） |
| 触发源 | 仅 Prometheus 映射 | 60+（Kafka/Redis/队列/CPU/内存/cron…） |
| 管理面 | monitoring ns 一套 adapter | keda ns 三个 Deployment |

**两者共存无冲突**（APIService 组不同：custom vs external），adapter 下线见 §5。

## 【原有功能】ScaledObject 语法详解

```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: <so名>                # 自动生成的 HPA 叫 keda-hpa-<so名>
  namespace: <与应用同 ns>
spec:
  scaleTargetRef: {name: <Deployment名>}   # 也支持 StatefulSet / 自定义资源
  pollingInterval: 15          # 秒；KEDA 轮询触发器周期（见下"注意"）
  cooldownPeriod: 300          # 缩容前等待秒数（默认300）
  minReplicaCount: 2           # 不写=0
  maxReplicaCount: 6
  advanced:
    horizontalPodAutoscalerConfig:
      behavior: {}             # 透传 HPA behavior（扩缩容速率）
  triggers:
  - type: prometheus
    metadata:
      serverAddress: http://prometheus-stack-kube-prom-prometheus.monitoring:9090
      query: sum(rate(http_requests_total{app="myapp"}[2m]))
      threshold: "100"         # 每副本平均值阈值（averageValue 语义）
      # authModes: "bearer"    # 需要 Token/TLS 时配合 TriggerAuthentication
```

常用触发器示例：

```yaml
# Kafka（按 lag 伸缩）
- type: kafka
  metadata:
    bootstrapServers: kafka.kafka:9092
    consumerGroup: my-group
    topic: my-topic
    lagThreshold: "1000"
# Redis 队列长度
- type: redis
  metadata:
    address: redis.redis:6379
    listName: task-queue
    listLength: "500"
# CPU/内存（基于 metrics-server，不需要 adapter）
- type: cpu
  metricType: Utilization
  metadata: {value: "70"}
```

## 【后补调整】（踩坑记录）

1. **首次启动 metrics-apiserver 卡 ContainerCreating（secret "kedaorg-certs" not found）**：
   自签证书由 operator 首次启动时生成（cert-controller rotator），存在约 1~2 分钟竞态，
   operator 日志可见 APIService 更新冲突重试（`the object has been modified`），均自愈。
   **无需处理**；只有 >5 分钟不恢复才需 `kubectl -n keda rollout restart deploy`。
2. **external metrics 查询路径不是 `s0`**：资源名 = `s<序号>-<触发器类型>`，且必须带
   labelSelector，否则报 `scaledObject name is not specified`。确切名字看 HPA：
   `kubectl -n keda-demo get hpa keda-hpa-demo-prom -o yaml | grep -A3 'metric:'`。
3. **threshold 语义是 averageValue（每副本）**：demo 初版 threshold=50 而本集群
   `sum(up)≈100`，HPA 立即想扩容 → 把 threshold 调到 300 保持 2 副本不扰动。
   写 ScaledObject 时先在 Prometheus 跑一遍 query 确认量级再定阈值。
4. **Harbor 新建了 `keda/` 私有项目**（此前不存在；向不存在的项目 push 会报
   `authentication required`，并非凭据错误）。

## 注意事项

- **不要手写 HPA 与 ScaledObject 并存**：同一工作负载的 HPA 归 KEDA 管，KEDA 会
  拒绝/接管被外部修改的 HPA（owner label），手写 HPA 会被删除或打架。
- **query 必须返回单值**（scalar 或单序列 vector），返回多序列会报错；空值时
  KEDA 按 0 处理（可配 `fallback` 兜底，避免误缩容）。
- **缩容到 0**：`minReplicaCount: 0` 时 Deployment 可缩到 0 并由 KEDA 重新拉起
  （依赖指标重新有值）；事件型建议用 ScaledJob。注意 pollingInterval 在
  min>0 时只影响状态刷新，不影响伸缩节奏（伸缩由 HPA 实时做）。
- prometheus 触发器默认匿名访问，跨 ns 用集群内 Service 地址即可
  （`http://prometheus-stack-kube-prom-prometheus.monitoring:9090`）。
- 升级 KEDA：换新 tgz 后 `bash /data1/ssdxt/monitoring/05-install-keda.sh`（幂等）。

## adapter 下线路线图（另行决策，本次不动）

prometheus-adapter 与 KEDA 当前共存（custom.metrics vs external.metrics，无冲突）。
下线 adapter 的前置条件：
1. 现有所有基于 custom.metrics 的 HPA 全部迁移为 KEDA ScaledObject（含
   TriggerAuthentication 管理 Prometheus 认证）；
2. 检查是否有 Grafana/脚本直接调用 custom.metrics API；
3. `helm -n monitoring uninstall prometheus-adapter` 并确认
   `v1beta1.custom.metrics.k8s.io` APIService 消失；
4. KEDA 可选启用 `metricsServer` 之外的 custom metrics provider（2.21 无此功能，
   若仍需 custom.metrics API，需保留 adapter 或改用 KEDA + external 写法）。

回滚（整个 KEDA 下线）：`helm -n keda uninstall keda && kubectl delete ns keda`；
所有 ScaledObject 的 HPA 由 KEDA 创建，随 uninstall 一并回收，业务 Deployment 副本数
保持 uninstall 前的值，不影响存量运行。
